## 一、执行摘要

**结论：当前不具备商业化条件，但底子好于预期，无需推翻重来。**

| 维度 | 打分 | 一句话评价 |
|---|---|---|
| 产品功能完整度 | 5 / 10 | 核心创作链路真实闭环；成片导出缺字幕/配音/音轨 |
| 安全工程 | 4.5 → 7 / 10 | 代码层安全设计高于行业平均；硬化批次已落地，HTTPS 待部署时补 |
| 商业化基础设施 | 1.5 / 10 | 支付/计费/配额为零，但有正确的数据与权益地基 |
| 账号体系与后端 | ~6 / 10 | 认证/隔离/网关已实现并已提交，E2E 验证待做 |

核心价值：Script → Asset → Keyframe → Video 全链路真实可用，对接阿里/DeepSeek/火山/MiniMax 四家供应商的文本/图片/视频模型，含审核拦截、重试降级、流式输出。差的不是架构，是**生产化收尾、计费层、成片交付力**三块。

**总距离：约 2~3 个月认真迭代可达「可以公网收钱」。**

### 第 4 批：admin 可视化页面（约 4~5 人日）

**信息架构**（新增 `components/admin/`，`/admin` 路由 + role 守卫）：

```

/admin/users          → 用户管理：列表搜索、状态徽标、VIP 发放（日期选择）/撤销、禁用（二次确认+密码再认证）
```

**技术要点**：

- 组件：`AdminLayout`、`UsersTable`、`VipGrantDialog`、`DisableUserDialog`、`DashboardStats`。
- 测试：组件测试 + 一个 service 层封装 `services/adminClient.ts`（统一 CSRF 头）。

### 第 5 批：公告系统 + 站内通知中心（约 5 人日）

**公告（announcements）**：

```sql
-- 004_announcements.sql
CREATE TABLE announcements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  title VARCHAR(200) NOT NULL,
  body TEXT NOT NULL,
  level VARCHAR(16) NOT NULL DEFAULT 'info',      -- info|warning|critical
  starts_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  ends_at TIMESTAMPTZ,                             -- NULL = 长期
  created_by UUID NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

- API：`GET /api/announcements/active`（公开/登录皆可）；admin CRUD 走 `/api/admin/announcements`（再认证）。
- 前端：`AnnouncementBanner`（按 level 着色，critical 强提示），Dashboard 顶部轮播历史公告。

**通知中心（notifications）**——复用 outbox 模式（事务内写、worker 消费）：

```sql
-- 005_notifications.sql
CREATE TABLE notifications (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id),
  kind VARCHAR(32) NOT NULL,          -- vip_expiring|job_done|job_failed|system|credit_low
  payload JSONB NOT NULL DEFAULT '{}',
  read_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON notifications (user_id, created_at DESC) WHERE read_at IS NULL;
```

- 触发点：job 完成/失败（`pollJob` 终态时写）、VIP 到期前 3 天（outbox worker 顺带扫描）、余额低于阈值（第 6 批接入）。
- API：`GET /api/notifications`（分页、未读数）、`POST /api/notifications/:id/read`、`POST /api/notifications/read-all`。
- 前端：Sidebar 铃铛 + 未读徽标 + 通知抽屉；可选项：重要通知同时投递邮件（复用 email_outbox）。

### 第 6 批：计费层——免费增长期积分体系（约 2~3 周，详细设计见 §五）

里程碑顺序：**6a 调用计量 → 6b 免费配额（成本护栏）→ 6c 活动系统（签到/拉新/兑换码）**。**已拍板：支付、充值、会员售卖全部延后**——本期所有积分都来自活动/兑换码/注册赠送，会员三档作为预案冻结（§5.1.3），用户积累后开闸：补 6d 充值到账 + 6e paywall 即可（各约 3~5 天）。

### 第 7 批：成片交付力（约 2~4 周）

按优先级：
1. **字幕烧录**（ffmpeg.wasm subtitles filter；时间轴已有镜头/台词数据，先生成 SRT 再 burn-in）；
2. **TTS 配音**（接入火山/阿里 TTS，网关加 `tts` capability；音画对齐按镜头时长拼接音轨）；
3. **BGM**（素材库 + 音量 ducking）；
4. 转场/片头尾模板（低优先）。
涉及：`videoMerger.ts`（从 concat 扩展为 filter_complex 合成管线）、网关 presets 增加 TTS 协议、导出页交互重排。**注意 ffmpeg.wasm 单线程性能上限，长片合成需显示耗时预期或转服务端渲染（后续可选 FFmpeg 容器服务）。**

### 第 8 批：经营 dashboard + 对账（约 1~2 周）

- 聚合接口：`GET /api/admin/stats/overview`（DAU、注册漏斗、调用成功率、积分消耗、MRR）、`/stats/invocations?range=`。
- 对账：每日对账单（订单表 vs 渠道账单导入 CSV 比对）；发票走第三方开票服务对接或人工流程。
- 埋点：自建极简事件表 `analytics_events(user_id, event, props, created_at)`（注册→验证→建项目→首次生成→付费），不做重型方案。

## 五、商业化系统设计专篇

### 5.1 定价与会员体系（成本锚定版）

> **已拍板（2026-09-24）：首期不接在线支付**，线下收款 + 管理员到账 + 兑换码 + 活动；支付网关推迟（见 D4 / §5.5）。
> **已拍板（2026-09-24 二次确认）：会员与充值整体延后**——现阶段先免费积累用户，只上线配额 + 积分活动体系；会员三档（§5.1.3）作为**已设计完毕的预案冻结**，待种子用户量起来后一键开闸（admin 侧只需放开充值入口与调整注册赠送额度）。
> **成本结构（用户确认）**：大头 = 大模型调用（含语音识别/配音）+ 服务器固定费用。设计原则：**会员费覆盖服务器与功能权益，积分覆盖模型调用成本**，目标综合毛利 ≥ 40%。

#### 5.1.1 成本模型（单次上游成本估算，上线首月用真实账单校准）

| 项目 | 上游成本（估） | 依据 |
|---|---|---|
| 视频生成 5s（火山/通义，720p） | ¥1.2~2.0/次 | 最大的成本项，价格表须可热调 |
| 图片生成（wanx/doubao） | ¥0.05~0.15/张 | |

| 权益 | 体验版 Free | 创作者会员 ¥69/月 | 工作室会员 ¥199/月 |
|---|---|---|---|
| 注册/会员赠送积分 | 注册送 200 分（≈6 次视频，保证完整跑通一次全流程） | 每月 800 分（等效 ¥80，86 折） | 每月 2400 分（等效 ¥240，8 折） |
| 每日签到 | 2 分/天，连续 7 天封顶 10 分/天（月上限 ≈120 分） | 同左 | 同左 |
| 可用模型 | 基础档（access_level=free） | 全部模型（VIP 档） | 全部模型 |
| 每日配额（防滥用） | 文本 10 / 图片 3 / 视频 0 | 视频 20 次/天 | 视频 60 次/天 |
| 媒体存储配额 | 2GB | 20GB | 100GB |
| 成片导出 | 720p + 平台水印 | 1080p 无水印 | 1080p 无水印 + 批量导出 |
| 生成队列 | 普通 | 优先 | 最高优先 |
| 到期处理 | — | 降回 Free（积分永不过期，权益失效） | 同左 |

**线下充值积分包（对所有人开放，含 Free）**：¥10=100 分 / ¥50=550 分（9 折） / ¥100=1200 分（8 折） / ¥500=6500 分（7.7 折）。

**定价逻辑**：
- 会员费的积分部分按 8~8.6 折赠送——折扣 + 功能权益双重理由买会员，而不是单纯卖分；
- 视频对 Free 关闭（配额 0）是**最重要的付费墙**：创作刚需 + 成本最贵，双重动机升级；
- 服务器固定成本由会员费底盘覆盖：粗算 30 个创作者会员（¥2070）即覆盖 ¥150~300 服务器 + 赠送积分的预期消耗；
- 水印去除/1080p/存储/队列是零边际成本权益，用功能感而不是降价驱动订阅；
- 获客成本核算：拉新奖励总成本 ≈ ¥20~30/有效用户（300 分 + 上游消耗），相对 ¥69/月 ARPU 可接受，且发放条件绑定真实使用（§5.4）。

### 5.2 数据模型（DDL 草案，`006_billing.sql`）

> 支付相关的 `orders` / `subscriptions` / `plans` 三张表**暂缓**，等接支付网关时再加；本期只落积分核心 + 活动。

```sql
-- ============ 积分核心（本期） ============

CREATE TABLE credit_accounts (
  user_id UUID PRIMARY KEY REFERENCES users(id),
  balance INT NOT NULL DEFAULT 0 CHECK (balance >= 0),
  low_threshold INT NOT NULL DEFAULT 50,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- 流水只增不改（对账与争议追溯的唯一事实源）
CREATE TABLE credit_ledger (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL REFERENCES users(id),
  delta INT NOT NULL,                             -- 负=消耗 正=入账
  balance_after INT NOT NULL,
  reason VARCHAR(32) NOT NULL,                    -- signup_grant|admin_grant|redeem|checkin
                                                  -- |referral|invocation|refund|revoke
  ref_type VARCHAR(32),                           -- redeem_code|invocation|admin_action
  ref_id UUID,
  note VARCHAR(200),                              -- admin 充值备注（线下转账流水号等）
  idempotency_key VARCHAR(80) UNIQUE,             -- 例: inv:<invocation_id> / ck:<user>:<date>
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON credit_ledger (user_id, created_at DESC);

-- ============ 活动：签到 ============

CREATE TABLE check_ins (
  user_id UUID NOT NULL REFERENCES users(id),
  checkin_date DATE NOT NULL,
  streak INT NOT NULL DEFAULT 1,
  credits_awarded INT NOT NULL,
  idempotency_key VARCHAR(80) UNIQUE,             -- ck:<user_id>:<date>（防同日重复）
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  PRIMARY KEY (user_id, checkin_date)
);

-- ============ 活动：兑换码 ============

CREATE TABLE redeem_batches (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name VARCHAR(100) NOT NULL,                     -- 批次备注：如「国庆活动」「线下卡密」
  credits INT NOT NULL,
  total_codes INT NOT NULL,
  max_redemptions_per_user INT NOT NULL DEFAULT 1,
  expires_at TIMESTAMPTZ,
  created_by UUID NOT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE redeem_codes (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  batch_id UUID NOT NULL REFERENCES redeem_batches(id),
  code_hash BYTEA NOT NULL UNIQUE,                -- SHA-256，只存哈希；明文仅在生成时一次性导出
  redeemed_by UUID REFERENCES users(id),
  redeemed_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX ON redeem_codes (batch_id) WHERE redeemed_by IS NULL;

-- ============ 活动：拉新 ============

ALTER TABLE users ADD COLUMN referral_code VARCHAR(12) UNIQUE;   -- 注册后首次访问活动页时生成

CREATE TABLE referrals (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  referrer_id UUID NOT NULL REFERENCES users(id),
  referee_id UUID NOT NULL UNIQUE REFERENCES users(id),  -- 一人只能被邀一次
  referrer_rewarded_at TIMESTAMPTZ,                       -- NULL = 未达发放条件
  referee_rewarded_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

设计要点：
- **券码只存哈希**：明文码生成后一次性导出（CSV 给运营），库内泄露也无法冒用；
- 所有入账都过 `credit_ledger` 且带唯一 `idempotency_key`（签到 `ck:<user>:<date>`、兑换 `rc:<code_id>`、拉新 `ref:<referral_id>:r|e`）——**重放天然安全**；
- `users` 相关扩展：VIP 权益继续走 `user_entitlements`（线下充值月卡 = admin 发 VIP + expires_at），**不新增并列体系**。

### 5.3 计量与扣费流程（集成点：`model-gateway/gateway.js`）

```
POST /api/model-invocations
  ├─ 中间件 quotaGuard：per-user 日配额（免费层）+ 全局限流（新增 invocationLimiter，
  │   keyFn: req.ip，与登录限流同款实现）——超限 429 + 升级提示码 QUOTA_EXCEEDED
  ├─ 读取 model + capability → creditsFor(capability, preset) 价格表（plans 之外单独 config 表，
  │   admin 可改价）
  ├─ 事务内预检：SELECT balance FROM credit_accounts WHERE user_id=$1 FOR UPDATE
  │   → 余额不足：402 CREDIT_REQUIRED（前端 paywall 弹窗）
  ├─ insertInvocation（现有幂等逻辑不动）→ 同事务写 credit_ledger（idempotency_key = inv:<id>）
  │   与 UPDATE credit_accounts SET balance = balance - cost
  ├─ invokeSync / createAsyncJob（现逻辑）
  └─ 失败回滚规则：UPSTREAM_ERROR 且未产生上游消耗 → ledger 补 refund 记录（幂等 key refund:<id>）；
      submission_uncertain → 冻结不退，人工/对账后处理（与现有语义一致）
```

关键点：
- **扣费与 invocation 同事务**，杜绝「调用成功没扣钱 / 扣了钱没记录」；
- `credit_ledger.idempotency_key` 唯一索引天然防重（Idempotency-Key 重放不会双扣）；
- 价格表放 `system_settings`（key: `credit_price`），admin 后台可调，无需发版；
- 每次调用结果里返回 `creditsRemaining`，前端展示。

### 5.4 线下充值、兑换码与活动系统

> **节奏说明**：本节的「线下充值」流程属于**延后预案**（会员开闸时启用）；现阶段先上兑换码 + 签到 + 拉新（API 表中前四行 + 活动部分），admin 充值接口随开闸一并交付。

#### 线下充值流程（预案）

```
用户在「充值」页看到收款码 + 管理员联系方式 → 线下转账（备注用户邮箱）
→ 管理员在 admin 后台核对收款记录 → POST /api/admin/users/:id/credits {delta, note}
   （requireAdmin + 再认证 + adminLimiter + 审计；note 记录转账流水号）
→ 同事务写 credit_ledger（reason=admin_grant, idempotency_key=admin:<uuid>）与余额
→ 用户端立即到账（Sidebar 余额刷新），并收到站内通知（第 5 批 notifications）
```

- admin 后台充值入口放在第 4 批的用户管理页（用户行内「充值」按钮 + 金额/备注弹窗）；
- 对账方式（首期）：admin 自维一张收款截图/表格即可；月度人工核对 `credit_ledger WHERE reason='admin_grant'` 与实际收款是否一致；
- 月卡/会员：同样线下收款后 admin 调用现有 `POST /api/admin/users/:id/vip`（expiresAt 按月设置）。

#### API 设计（新增路由前缀 `/api/credits`，全部 requireUser + CSRF）

| 接口 | 说明 | 幂等/防薅 |
|---|---|---|
| `GET /api/credits/balance` | 余额 + 最近流水（分页） | — |
| `POST /api/credits/checkin` | 今日签到，返回 streak 与奖励 | `ck:<user_id>:<date>` 唯一；连续中断重置 streak |
| `POST /api/credits/redeem` `{code}` | 兑换码核销 | 码只存哈希（SHA-256 后查库）；`rc:<code_id>` 幂等；受批次 `max_redemptions_per_user` 与 `expires_at` 约束；接口限流 5 次/时（防爆破，复用 rateLimit） |
| `GET /api/credits/referral` | 我的邀请码 + 已邀请列表 + 奖励状态 | — |
| `POST /api/credits/redeem` 等 | 所有入账同事务：ledger + balance，见 §5.2 | — |

**签到逻辑**：`checkin_date` 按用户本地时区取日；streak = 昨日有签到则 +1 否则重置 1；奖励 = `min(基础分 + streak 递增, 上限)`，参数存 `system_settings`（`checkin_base_credits`、`checkin_max_credits`），admin 可热调。

#### 拉新流程与防薅

```
A 在「邀请」页复制专属码/链接（?ref=<code>）→ B 注册时填码（或链接自动带入）
→ 注册成功即写 referrals（referee 唯一约束：一人只能被邀一次）
→ B 邮箱验证通过 → B 立即得 50 分（ledger reason=referral, key=ref:<id>:e）
→ B 完成首次成功 AI 调用（首条 status='succeeded' 的 invocation 落库时检查）
   → A 得 100 分（key=ref:<id>:r）+ 站内通知
```

**防薅四道闸**（对抗批量注册薅积分）：
1. 奖励分批发放：被邀人奖励快、邀请人奖励**延后到真实使用**——批量注册只能拿到小头；
2. 注册链路已有的限流 + 邮箱验证（一次性 token）抬升成本；
3. `referrals.referee_id UNIQUE` + 注册 IP 限流（现有 limiter）+ 同邮箱域名批量注册可后续加黑名单；
4. 所有活动入账都有流水可查，异常模式（同 IP 注册、同段邮箱、深夜批量）可在 admin 侧 `credit_ledger + audit_events` 联查发现，支持 `reason=revoke` 追回。

#### 前端（第 6 批新增组件）

- `CreditBadge`：Sidebar 积分余额（< 阈值变红，点击进充值页）；
- `RechargePage`：收款码图片（`system_settings` 存 URL，admin 可换）+ 兑换码输入框 + 活动说明；
- `CheckinCard`：签到日历 + 今日按钮 + 连续天数；

- `PaywallDialog`：402/429 拦截弹窗（余额不足 → 引导充值/兑换/签到，不再出现任何「在线支付」入口）；
- 移除前端所有「立即购买」GitCC 外链（`ModelManagerTab.tsx:174`、`Onboarding/ApiKeyPage.tsx:125`）。

9. 禁用用户 → 其会话立即失效；
10. 备份恢复演练：dump → 重建 → 数据完整；
11. HTTPS：HTTP 跳转、HSTS 头、Cookie Secure 标志；
12. 审计抽查：敏感操作在 audit_events 有对应记录且 IP 已 HMAC。

## 八、战略决策点

| # | 决策 | 选项与建议 |
|---|---|---|
| D1 | 开源协议 vs 收费 | **双轨制（推荐）**：SaaS 托管版收费 + 自部署社区版 MIT 免费；或双许可证（核心闭源）。否则自部署免费版会持续吃掉付费用户 |
| D2 | 产品形态 | **主推 SaaS 托管版（推荐）**：技术栈就绪、计费层通用；Electron 降级为「远端 Web 客户端壳」（与 rollout 计划一致）；桌面订阅需另建 license/激活体系，不建议首期做 |
| D3 | API Key 叙事 | 收费前必须统一为「平台额度」模式（用户买积分、平台管上游 key）；GitCC 导流文案移除 |
| D4 | 支付渠道 | **已拍板（2026-09-24）：支付、充值、会员售卖全部延后**——现阶段免费积累用户（配额兜成本 + 活动做增长），会员三档作为预案冻结，用户量起来后开闸（先线下充值，支付网关再往后）。若后续走桌面订阅需另建 license/激活体系，仍不建议首期做 |
| D5 | 公司主体/ICP/等保 | SaaS 国内运营需 ICP 备案（已有 coderx.me 域名可作基础）；收款需对公主体；生成内容需接入审核（现有审核拦截提示是上游模型自带，平台侧需免责条款与举报入口） |
