# 漫剧工场 部署手册

> 商业化实施方案第 3 批承诺交付物（env 清单 + 命令 + 回滚步骤）。
> 适用形态：docker compose 生产部署（nginx 前端 + Express api + postgres 16）。
> 部署基线分支：`feat/public-model-platform`。
> 配套文档：《商业化审计与实施方案-2026-09.md》§6（拓扑/备份）、`docs/database-rollback.md`（迁移回滚）。

**形态说明（对应目标设计，均已落地）**：api 镜像内置 `postgresql16-client` 与 `age`（`server/Dockerfile.server`），备份脚本 `server/scripts/backup-db.js` 打进镜像；compose 为 api 挂载 `backups:/app/backups` 命名卷并透传 `BACKUP_*` 变量；备份加密开关 `BACKUP_AGE_RECIPIENT`（`server/scripts/backup-encrypt.js`）；mailpit 由 compose `profiles: ["dev"]` 门控，生产默认不启动；全服务日志 json-file 10m × 3 轮转；TLS 方案 A 的 `docker-compose.tls.yaml` 与 `deploy/nginx-tls.conf` 已随仓库提供。本手册所有命令均与仓库当前文件一一对应。

## 1. 前置条件

| 项目 | 要求 | 说明 |
|---|---|---|
| 域名与 DNS | 一条 A 记录指向服务器公网 IP | 如 `manga.example.com`，先配好再跑 certbot |
| ICP 备案 | 国内 SaaS **必需**，启动要早（通常 1–3 周） | 未备案域名在国内服务器无法通过 80/443 提供服务 |
| 服务器架构 | **amd64（x86_64）** | 本地开发机是 macOS arm64，镜像架构不一致（见 §3.7） |
| Docker | Docker Engine + **Compose v2**（`docker compose version` 可用） | TLS override 的 `!override` 标签需 v2.24+ |
| 磁盘 | ≥ 20 GB | postgres 数据卷（含 base64 媒体）+ 备份卷 + 镜像层都会增长 |
| 端口 | 开放 80/443 | 5432（postgres）、3001（api）不出内网，无需开放 |
| 生产 SMTP | **真实账号**：`SMTP_USER` / `SMTP_PASSWORD` 必须是可发信的真实账号 | 否则验证邮件发不出，用户无法注册；推荐企业邮箱或邮件推送服务的 SMTP + 授权码 |
| 安全基线 | `.env` 权限 600、不进 git（`.gitignore` 已覆盖） | 7 个强制密钥只在 `.env`，不写进代码 |

## 2. 环境变量清单

完整变量表，变量名与 `.env.example` 逐一对应（共 32 个；禁止从本地 `.env` 抄值，所有密钥现场生成）。**✅ 必须**＝docker-compose.yaml 用 `${VAR:?...}` 强制校验，缺失拒绝启动（共 7 个）。

| 变量 | 必填 | 用途 | 生成方式 / 生产取值 |
|---|---|---|---|
| `DB_HOST` | 否 | api 连库主机，容器编排下由 compose 固定 | `postgres`（compose 已固定） |
| `DB_PORT` | 否 | 数据库端口 | `5432` |
| `DB_NAME` | 否 | 数据库名 | `manga_studio` |
| `DB_USER` | 否 | 数据库用户 | `postgres` |
| `DB_PASSWORD` | 否 | 仅本地开发用；容器部署时 compose 用 `POSTGRES_PASSWORD` 注入 | 留空，以 `POSTGRES_PASSWORD` 为准 |
| `NODE_ENV` | 否 | compose 把 api/frontend 固定为 `production`，此处仅影响本地脚本 | `production`（compose 固定） |
| `CORS_ORIGINS` | ✅ 必须 | 登录/注册 CORS 与匿名写操作白名单，非白名单源一律 403 | `https://<你的域名>`（精确源、无尾斜杠、禁 `*`） |
| `PUBLIC_APP_URL` | ✅ 必须 | 邮件链接与安全判断的规范站点地址；管理员引导 URL 也基于它 | `https://<你的域名>`（无尾斜杠） |
| `COOKIE_SECURE` | 否 | Cookie Secure 标志，`NODE_ENV=production` 下自动开启 | 生产无需设置 |
| `IP_HMAC_SALT` | ✅ 必须 | IP 审计值 HMAC 加盐 | `openssl rand -hex 32` |
| `SMTP_HOST` | 生产必填 | SMTP 服务器 | 如 `smtp.exmail.qq.com` |
| `SMTP_PORT` | 否 | SMTP 端口 | `587`（默认） |
| `SMTP_SECURE` | 否 | 是否直连 TLS | `465` 端口→`true`，`587`→`false` |
| `SMTP_REQUIRE_TLS` | 否 | 是否强制 STARTTLS | `true`（默认） |
| `SMTP_USER` | 生产必填 | SMTP 账号，**必须真实** | 完整邮箱地址 |
| `SMTP_PASSWORD` | 生产必填 | SMTP 密码/授权码 | 服务商授权码 |
| `SMTP_FROM` | 否 | 发件人地址 | `no-reply@<你的域名>`（默认占位值必须改掉） |
| `EMAIL_DELIVERY_KEY` | ✅ 必须 | 邮件 outbox 动作令牌加密封装密钥（32 字节 hex） | `openssl rand -hex 32` |
| `EMAIL_DELIVERY_KEY_ID` | 否 | 封套密钥版本号 | `v1` |
| `EMAIL_VERIFICATION_DISABLED` | ⚠️ 仅本地开发 | `true` 时注册直接激活账号、不发验证邮件（本地无 SMTP 时的逃生阀）。**生产绝对不要设为 true**——等于任何人注册即可登录，绕过邮箱归属验证 | 生产留空/false |
| `ARGON2_MEMORY` | 否 | Argon2id 内存（KiB） | `65536`（生产基线 64MiB） |
| `ARGON2_ITERATIONS` | 否 | Argon2id 迭代次数 | `3` |
| `ARGON2_PARALLELISM` | 否 | Argon2id 并行度 | `1` |
| `BOOTSTRAP_ADMIN_EMAIL` | 否 | 首个管理员引导邮箱：`bootstrap-admin.js` 未传 `--email=` 时读取；仅用于创建引导令牌，**密码永远不走环境变量** | `admin@<你的域名>` |
| `BACKUP_INTERVAL_HOURS` | 否 | 自动备份间隔（小时） | `24`（默认，compose 已透传） |
| `BACKUP_INITIAL_DELAY_MS` | 否 | api 启动后首次备份延迟（毫秒） | `600000`（10 分钟） |
| `BACKUP_KEEP` | 否 | 备份保留份数 | `14`（默认） |
| `BACKUP_DISABLED` | 否 | `true` 关闭自动备份调度器 | `false` |
| `BACKUP_AGE_RECIPIENT` | 生产强烈建议 | age 公钥；设置后备份自动加密为 `.dump.age` 并**删除明文**，不设置则明文落盘（含用户 PII）并在日志告警 | `age-keygen` 输出的 `Public key: age1...` |
| `MODEL_ENC_KEY` | ✅ 必须 | 模型网关凭据/结果 AES-256-GCM 密钥；缺失时生产 fail-close 拒绝启动 | `openssl rand -hex 32` |
| `MODEL_ENC_KEY_ID` | 否 | 凭据封套密钥版本 | `v1` |
| `REQUEST_HMAC_KEY` | ✅ 必须 | 模型调用请求哈希 HMAC 密钥 | `openssl rand -hex 32` |
| `POSTGRES_PASSWORD` | ✅ 必须 | postgres 数据库口令（compose 强制注入，杜绝默认弱口令） | `openssl rand -hex 32` |

密钥速查（7 个强制项全部可用同一条命令生成，逐个复制）：

```bash
openssl rand -hex 32
```

备份加密公钥（需先安装 age：macOS `brew install age`，Linux `apt install age` 或官方 release）：

```bash
age-keygen
# 输出：Public key: age1...   ← 填入 BACKUP_AGE_RECIPIENT
# 同目录生成的身份文件（私钥）务必离线保管，丢失 = 备份永久无法解密
```

## 3. 首次部署 step-by-step

### 3.1 克隆代码

```bash
git clone <仓库地址> gcc-printfilm && cd gcc-printfilm
git switch feat/public-model-platform   # 部署基线分支；合入主干后以主干为准
```

### 3.2 生成 .env

```bash
cp .env.example .env
chmod 600 .env
```

按 §2 表格逐项填写；7 个强制密钥用 `openssl rand -hex 32` 现场生成。关键是：

- `CORS_ORIGINS=https://<你的域名>`、`PUBLIC_APP_URL=https://<你的域名>`（一开始就走 TLS 就直接填 https，避免 §4 收尾时再改）；
- `SMTP_USER` / `SMTP_PASSWORD` 必须真实可用，否则注册流程卡在验证邮件；
- `BOOTSTRAP_ADMIN_EMAIL` 填管理员邮箱（也可在 3.5 用 `--email=` 传入）；
- 建议立即设置 `BACKUP_AGE_RECIPIENT`（§6.1）。

### 3.3 启动

```bash
docker compose --env-file .env up -d --build
```

- frontend 构建上下文为仓库根目录（`Dockerfile`，node:22-alpine 构建 + nginx:alpine 运行）；api 构建上下文为 `./server`（`server/Dockerfile.server`，已内置 `postgresql16-client` 与 `age`）。
- postgres 只在 `pgdata` 卷为空的**首次启动**时应用 `POSTGRES_PASSWORD`；之后改口令见 §7.2 警示。

### 3.4 健康检查

```bash
docker compose ps                                  # 服务均 healthy/running
docker compose logs --tail 50 api                  # 应看到 [DB] Tables initialized 与监听 3001
curl -s http://127.0.0.1:3005/api/health           # 期望 {"status":"ok",...}
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3005/   # 期望 200
```

> 3005 是 frontend(nginx) 的宿主映射端口；启用 §4 TLS 后改用 443 域名访问，3005 收回。

### 3.5 引导首个管理员（维护模式 + 一次性 token）

`server/bootstrap-admin.js` 的硬性流程：先开维护模式 → 引导脚本拒绝在已有 active 管理员时重复执行 → 生成 24 小时有效、一次性使用的 setup URL → 在受保护终端打开该 URL 设置密码后账号激活。

```bash
# 1) 打开维护模式（config 表，JSONB 值；bootstrap 前置校验）
docker compose exec postgres psql -U postgres -d manga_studio \
  -c "INSERT INTO config (key, value) VALUES ('maintenance_mode', 'true'::jsonb)
      ON CONFLICT (key) DO UPDATE SET value = 'true'::jsonb;"

# 2) 生成引导令牌（等价写法：docker compose exec api npm run admin:bootstrap -- --email=<管理员邮箱>）
docker compose exec api node bootstrap-admin.js --email=<管理员邮箱>
```

脚本输出一条 `Bootstrap admin created (pending verification).` 与 setup URL（形如 `https://<你的域名>/#/bootstrap?token=...`）：

- 该 URL **只显示一次**、24 小时有效、token 一次性消费（`user_action_tokens`，purpose `bootstrap_admin`）；
- 在受保护终端/受信浏览器打开，页面设置密码后即完成激活（后端为 `POST /api/auth/bootstrap-complete`：写入密码哈希、标记邮箱已验证、状态转 active）；
- 若 URL 打不开，检查 `.env` 的 `PUBLIC_APP_URL` 是否已是公网 https 域名——引导 URL 由它拼出。

```bash
# 3) （可选）关闭维护模式——当前版本该标志仅约束 bootstrap 流程
docker compose exec postgres psql -U postgres -d manga_studio \
  -c "UPDATE config SET value = 'false'::jsonb WHERE key = 'maintenance_mode';"
```

### 3.6 配置模型 Provider

- 管理员登录后进入 **Admin 面板** 登记上游 Provider（Base URL / API Key / 模型清单）：凭据在服务端用 `MODEL_ENC_KEY`（AES-256-GCM）加密落库，缺失该密钥时生产环境拒绝启动；
- 或由用户在产品内通过迁移向导导入既有模型配置，绑定到网关模型后再调用；
- 配置完成后建议在 staging 上按实施方案 §7.2 清单做一次真实上游 E2E（该验证尚未完成，见 §8）。

### 3.7 镜像架构（macOS arm64 → 服务器 amd64）

**推荐路径：直接在服务器上构建**（compose build 天然产出 linux/amd64，无需交叉编译）：

```bash
docker compose --env-file .env up -d --build
```

备选路径：在本地（或 CI）用 buildx 构建并推送 amd64 镜像，服务器只拉取：

```bash
docker buildx build --platform linux/amd64 \
  -t <镜像仓库>/<命名空间>/manga-studio:<tag> --push .
docker buildx build --platform linux/amd64 \
  -f server/Dockerfile.server -t <镜像仓库>/<命名空间>/manga-studio-api:<tag> --push ./server

# 服务器上：
docker pull <镜像仓库>/<命名空间>/manga-studio:<tag>
docker pull <镜像仓库>/<命名空间>/manga-studio-api:<tag>
docker compose --env-file .env up -d        # 本地已有同名镜像时不再 --build
```

> 拉取镜像模式下 compose 检测到本地已存在 `image:` 同名镜像即直接使用；首次使用建议 `docker compose up -d` 后用 `docker compose images` 核对架构为 `amd64`。

## 4. TLS 与域名

目标拓扑（实施方案 §6.1）：`用户 →(443 HTTPS)→ frontend(nginx) [TLS 终止] ├ / → 静态资源 └ /api/ → api:3001（内网）`；生产收回 3005，仅保留 443（80 只做跳转）。

### 4.1 方案 A：仓库 TLS override（nginx 容器直接终止 TLS，推荐）

仓库已提供两个文件：`docker-compose.tls.yaml`（override，把 frontend 端口整体替换为 80/443）与 `deploy/nginx-tls.conf`（443 server 块 + 80→443 跳转 + `/api/` 反代 + HSTS + CSP 基线）。

**第 1 步：签发证书**（宿主机 certbot；DNS 验证适用于无法开放 80 或通配符场景）：

```bash
# HTTP-01（需 80 端口空闲：先 docker compose stop frontend）
sudo certbot certonly --standalone -d <你的域名> --agree-tos -m <证书通知邮箱> -n
# 或 DNS 验证：
sudo certbot certonly --manual --preferred-challenges dns -d <你的域名> --agree-tos -m <证书通知邮箱>
```

**第 2 步：把证书拷入约定目录**（override 挂载 `./deploy/certs → /etc/nginx/certs`，目录首次需创建）：

```bash
mkdir -p deploy/certs
sudo cp -L /etc/letsencrypt/live/<你的域名>/fullchain.pem deploy/certs/
sudo cp -L /etc/letsencrypt/live/<你的域名>/privkey.pem  deploy/certs/
```

**第 3 步：核对 `deploy/nginx-tls.conf`**：文件内 `server_name _` 为占位（任意 Host 均匹配），上线建议把 80/443 两个 server 块中的 `server_name _` 改为 `<你的域名>`；证书路径固定为容器内 `/etc/nginx/certs/fullchain.pem` 与 `/etc/nginx/certs/privkey.pem`（与挂载约定一致，无需改动）；HSTS 默认已启用（`max-age=31536000; includeSubDomains`）。

**第 4 步：同步 `.env`**：`CORS_ORIGINS` 与 `PUBLIC_APP_URL` 必须是 `https://<你的域名>`；若此前填的是 http，改完随下一步 `up -d` 重建 api 生效（否则登录 403、邮件链接是 http）。

**第 5 步：以 override 启动并验证**：

```bash
docker compose --env-file .env -f docker-compose.yaml -f docker-compose.tls.yaml up -d
curl -sI https://<你的域名>/ | head -n 1          # 期望 HTTP/2 200（或 HTTP/1.1 200）
curl -s https://<你的域名>/api/health             # 期望 {"status":"ok",...}
curl -sI http://<你的域名>/ | head -n 1           # 期望 301，Location 指向 https
```

**第 6 步：自动续期**（certbot 自带 timer 续期后把新证书同步进 `deploy/certs/` 并 reload）：

```bash
sudo certbot renew --dry-run
# 续期钩子示例（crontab/systemd timer 由 certbot 管理）：
sudo certbot renew --deploy-hook "cp -L /etc/letsencrypt/live/<你的域名>/fullchain.pem /etc/letsencrypt/live/<你的域名>/privkey.pem <项目目录>/deploy/certs/ && cd <项目目录> && docker compose -f docker-compose.yaml -f docker-compose.tls.yaml exec frontend nginx -s reload"
# 钩子嫌复杂时可改为 restart frontend（秒级中断）
```

`docker-compose.tls.yaml` 全文（已入库，此处列出以便核对；以仓库文件为准）：

```yaml
# TLS 生产覆盖文件：与主 compose 叠加使用（Docker Compose v2.24+ 支持 !override 标签）。
services:
  frontend:
    ports: !override
      - "80:80"
      - "443:443"
    volumes:
      - ./deploy/nginx-tls.conf:/etc/nginx/conf.d/default.conf:ro
      - ./deploy/certs:/etc/nginx/certs:ro
```

### 4.2 方案 B：宿主层反代终止 TLS（Windows Server 场景）

服务器为 Windows Server、不便跑 certbot/容器 TLS 时，由宿主 IIS / nginx for Windows / Caddy 终止 TLS 后转发到宿主映射端口（不使用 `docker-compose.tls.yaml`，直接用主 compose）：

1. compose 保持默认（frontend 已映射 `3005:80`）；建议将绑定改为 `127.0.0.1:3005:80` 只收回环（属 compose 调整，需另行提交）。
2. **Caddy（最简，自动签发续期证书）**——Caddyfile：

   ```text
   <你的域名> {
       reverse_proxy 127.0.0.1:3005
   }
   ```

   启动：`caddy start --config Caddyfile`（生产建议注册为 Windows 服务）。
3. **IIS**：安装「URL 重写 + Application Request Routing」，在 ARR 功能设置里启用代理；站点绑定 443 并导入证书（`wacs`/win-acme 可自动申请 Let's Encrypt）；添加反向代理规则指向 `http://127.0.0.1:3005`。
4. **nginx for Windows**：`server { listen 443 ssl; ... location / { proxy_pass http://127.0.0.1:3005; } }`，证书路径指向宿主证书。
5. Windows 防火墙放行 80/443；3005 不暴露公网。
6. `.env` 同样要求 `CORS_ORIGINS` / `PUBLIC_APP_URL` 为 `https://<你的域名>`；HSTS 在宿主反代层加 `Strict-Transport-Security: max-age=31536000`。
7. 注意点：`deploy/nginx-tls.conf`（及主 `nginx.conf`）固定一跳 `X-Forwarded-For $remote_addr`；再套一层宿主反代时，api 记录到的客户端 IP 是宿主反代地址，按 IP 限流/审计会归并（见 §8；需要精确来源时让宿主反代透传真实 IP 并由前端 nginx 转发，属代码侧调整）。

## 5. 日常运维

### 5.1 更新发布

```bash
cd <项目目录>
git pull
docker compose --env-file .env up -d --build
docker compose logs -f api          # 观察启动与迁移日志
```

- **迁移自动应用**：api 启动时按文件名字典序执行 `server/migrations/*.sql`，每个迁移独立事务，已应用记录写入 `schema_migrations`（filename 主键 + applied_at），重启自动跳过（`server/db.js` 迁移 runner）。日志中 `[DB] Applied migration ...` 即本次新应用的迁移。
- 清理旧镜像释放磁盘（可选）：`docker image prune -f`。

### 5.2 日常查看

```bash
docker compose ps                       # 服务与健康状态
docker compose logs -f api              # api 日志跟随
docker compose logs --tail 200 frontend # nginx 访问/错误日志
docker compose logs -f postgres
```

日志已被 compose 限速（每服务 json-file `max-size 10m`、`max-file 3`，见主 compose 的 `x-default-logging`），不会无限膨胀。

### 5.3 磁盘

```bash
docker system df                              # 镜像/卷/缓存占用
docker compose exec api du -sh /app/backups   # 备份卷占用（约 = 14 × 单份备份大小）
```

增长来源与处置：① `pgdata` 卷——项目/资产以 JSONB（含 base64 媒体）入库，随用户量增长；② `backups` 卷——按 `BACKUP_KEEP` 自动轮转；③ 旧镜像层——`docker image prune -f`。磁盘余量建议保持 ≥ 20%。

## 6. 备份与恢复

### 6.1 自动备份机制

- api 启动即拉起调度器（`server/backup.js`）：每 `BACKUP_INTERVAL_HOURS`（默认 24）小时执行一次全库 `pg_dump`（custom 格式），首次在 `BACKUP_INITIAL_DELAY_MS`（默认 10 分钟）后；`BACKUP_DISABLED=true` 关闭。
- 备份写入 `backups:/app/backups` 命名卷，按 `BACKUP_KEEP`（默认 14）轮转（`.dump` 与 `.dump.age` 一并计数），自动清理更旧的。调度器与备份脚本同布局（`server/scripts/backup-db.js`，容器内 `/app/scripts/`），路径回归由 `server/test/backup-scheduler-path.test.js` 防护。
- **加密开关**：`.env` 设置 `BACKUP_AGE_RECIPIENT=<age 公钥>` 后，备份自动加密为 `manga_studio-<YYYYMMDD-HHMMSS>.dump.age` 并**删除明文**；加密失败则整个备份失败，绝不留明文伪装成功。未设置则保留明文 `.dump` 并在日志输出 `WARNING ... PLAINTEXT`。明文 dump 含用户 PII，生产**必须**设置加密（审计方案 R1）。
- 宿主机开发环境也可直接 `npm run backup`（根 `package.json`，调用 `server/scripts/backup-db.js`，需本机装有与服务端对齐的 pg_dump 16）。

### 6.2 手动备份

```bash
docker compose exec api node scripts/backup-db.js     # 立即全库备份一份（镜像内含脚本与 pg_dump/age）
docker compose exec api ls -la /app/backups           # 查看备份列表
docker compose cp api:/app/backups/<备份文件名> ./     # 拷出宿主机（建议再同步异地）
```

### 6.3 恢复演练（建议每季度一次，实施方案 §6.3）

```bash
# 0) 前置：确认 .dump.age 备份已解密（在任意装有 age 的机器上；identity 即 age-keygen 生成的私钥文件）
age --decrypt -i <私钥文件> <备份文件名>.dump.age > <备份文件名>.dump

# 1) 把 dump 拷入 postgres 容器
docker compose cp <备份文件名>.dump postgres:/tmp/restore.dump

# 2) 演练：恢复到临时新库（不动线上库）
docker compose exec postgres createdb --username postgres manga_studio_restore
docker compose exec postgres pg_restore --host localhost --username postgres \
  --dbname manga_studio_restore /tmp/restore.dump
# 验证：表数量/关键行数抽样核对
docker compose exec postgres psql -U postgres -d manga_studio_restore -c "\dt"
docker compose exec postgres dropdb --username postgres manga_studio_restore

# 3) 真实恢复（覆盖线上库）：先停 api 防写入，并先另存当前库一份
docker compose exec postgres pg_dump --host localhost --username postgres \
  --dbname manga_studio --format custom --file /tmp/pre-restore.dump
docker compose cp postgres:/tmp/pre-restore.dump ./pre-restore.dump
docker compose stop api
docker compose exec postgres pg_restore --host localhost --username postgres \
  --dbname manga_studio --clean --if-exists /tmp/restore.dump
docker compose start api
curl -s http://127.0.0.1:3005/api/health && \
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3005/    # 启动验证
```

- 恢复后迁移 runner 幂等（`schema_migrations` 保证不重复应用）。
- 迁移级回滚/重放（逆 SQL、replay 语义）**不在本章展开**，统一见 `docs/database-rollback.md`。
- 异地容灾（rclone → 对象存储，保留 30 天）为规划项（审计方案 §6.3），落地前至少把 6.2 拷出的备份放到服务器之外的存储。

## 7. 回滚

### 7.1 应用回滚（代码/镜像）

```bash
# 代码回退：切回上一个可用版本并重建
git log --oneline -10
git switch <上一个可用版本 tag 或 commit>
docker compose --env-file .env up -d --build
curl -s http://127.0.0.1:3005/api/health
```

镜像仓库模式下则回拉旧 tag 镜像后 `docker compose --env-file .env up -d`（不带 `--build`）。

**迁移不可自动降级**：迁移 runner 只向前应用、无自动 down；回退代码不会撤销已应用迁移（`schema_migrations` 已记账）。若旧代码与已应用的新迁移不兼容（涉及数据改写/导入类迁移），按 `docs/database-rollback.md` 的逆操作 SQL + 备份恢复处理；优先顺序永远是：先 `pg_dump` 备份当前库 → 再动手。

### 7.2 配置回滚与密钥轮换

```bash
cp .env .env.bak.$(date +%Y%m%d)      # 任何 .env 变更前先备份
# ...修改 .env...
docker compose --env-file .env up -d   # 重建受影响容器生效
```

| 密钥 | 轮换影响 | 处置 |
|---|---|---|
| `MODEL_ENC_KEY` | **已存凭据不可解密**：上游 Provider API Key 用它 AES-256-GCM 加密落库（封套绑定 `MODEL_ENC_KEY_ID`），换钥后解密 fail-close 报错 | 轮换后必须在 Admin 面板**重新录入**所有 Provider 凭据；缺钥时生产拒绝启动 |
| `POSTGRES_PASSWORD` | postgres 镜像仅在 `pgdata` 卷为空的首次初始化应用该值；只改 `.env` 会导致 api 用新口令连不上旧库 | 先在库内改口令，再同步 `.env`：`docker compose exec postgres psql -U postgres -c "ALTER USER postgres WITH PASSWORD '<新口令>';"` 然后 `up -d` |
| `EMAIL_DELIVERY_KEY` | outbox 中未投递邮件的动作令牌以旧钥封装，换钥后无法开封 | 令相关用户重新触发验证/重置邮件即可 |
| `REQUEST_HMAC_KEY` | 模型调用请求哈希口径变化，历史哈希无法与新哈希匹配 | 不影响可用性；涉及按哈希对账的历史记录人工核对 |
| `IP_HMAC_SALT` | 审计 IP 哈希口径变化 | 仅影响审计比对，无需额外操作 |

回滚配置＝还原 `.env.bak` 后 `up -d`。**严禁** `docker compose down -v`（会连 `pgdata` 数据卷一起删除）；仅停服用 `docker compose stop` / `down`（不带 `-v`）。

## 8. 已知限制

1. **单实例假设**：限流为进程内存实现、备份/邮件 outbox 调度无 leader 锁——多副本会重复跑定时任务且限流失真；扩容前按实施方案 §6.2 改造（限流迁 Redis 或 PG 原子 UPSERT、定时任务加 `pg_try_advisory_lock`）。会话存 DB，天然可水平扩展。
2. **真实上游模型 E2E 未在 staging 打真**：全阶段端到端（注册→剧本→资产→关键帧→视频）按实施方案 §7.2 清单验证是第 3 批验收项，当前未完成。
3. **统计代码未接入**：教程号/增长渠道的转化数据回传未埋点，上线初期渠道效果无法自动归因。
4. **备份异地容灾未落地**：加密备份仍在单机卷内，rclone 同步对象存储为规划项；落地前请人工定期拷出。
5. **方案 B 的客户端 IP 归并**：见 §4.2 注意点 7。
6. mailpit 调试收信由 compose `profiles: ["dev"]` 门控：生产 `up -d` 默认不含；需要时 `docker compose --env-file .env --profile dev up -d` 显式启动，收信网页在 http://localhost:8025。
